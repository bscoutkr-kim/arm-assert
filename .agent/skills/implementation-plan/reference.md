## Scope & defect handling (범위·불량) — **필수**

### 0. 계획 유형 (문서 맨 앞에 명시)

계획서·채팅 계획에는 **이번 턴의 주 유형**을 반드시 밝힌다. 필요 시 **복수 유형**을 아래처럼 나눈다.

| 유형 | 목적 | 포함하면 안 되는 것(기본) |
|------|------|---------------------------|
| **버그 수정** | 재현된 불량을 **현상·원인에 맞게 닫기** | 요청 없는 신규 기능·새 UX·“기능 추가로 버그 해결” 우선안 |
| **신규 기능** | 사용자가 요청·승인한 **새 동작·설정·범위 확장** | 같은 패치에 끼워 넣은 무관한 버그 대량 수정(별도 합의 없이) |
| **검증·분석** | 리뷰·점검·로그/원장 분석·재현 조사·원인만 특정 | 코드 변경이 필요하면 **별도 “버그 수정” 또는 “신규 기능” 계획**으로 분리·승인 |

- **버그 수정** 계획이 주 유형이면, **신규 기능 계획**은 같은 문서의 **별도 섹션**에 두고 **승인 전에는 구현하지 않는다.**
- **검증·분석만** 하는 턴이면 코드 수정 계획을 섞지 않는다(수정이 떠오르면 다음 계획으로 분리).

### A. 사용자 요청과 무관한 “추가” 금지 (승인 전)

- 계획·구현·PR에 넣는 변경은 **사용자가 요청한 내용** 또는 **명시적으로 승인받은 범위**로만 제한한다.
- 리팩터, 편의 기능, 설정 확장, 로그 강화 등 **요청에 없는 새 동작**을 하려면:
  1. 채팅에 **무엇을 왜 추가하려는지** 한 번에 분명히 쓰고,
  2. **사용자 동의(승인)** 없이 코드에 반영하지 않는다.
- 이유: 버그 수정·작은 수정 중 임의 확장이 **새 결함·회귀**를 자주 만든다.

### B. 불량(버그) 분석·수정 시 순서

1. **신규 기능으로 버그를 고치지 않는다.** “새 옵션·새 분기·새 파이프라인을 넣으면 증상이 사라질 것 같다”는 식의 **기능 추가형 수정**은 **기본 안으로 제시하지 않는다.** 먼저 **현상에 직접 대응하는 최소 변경**(잘못된 값·누락된 전달·잘못된 가드·오타·조건 반전 등)으로 닫을 수 있는지 본다.
2. **재현·원인·최소 수정**으로 버그를 **닫는 것**을 첫 목표로 한다. 같은 패치에 “이것도 개선”을 섞지 않는다.
3. **최소 수정만으로 불가·불충분**하다고 판단될 때만:
   - **왜 최소안이 부족한지** 한두 문단으로 적고,
   - **신규 기능(동작 확장) 안**을 **별도 계획 유형**으로 작성해 사용자 **승인**을 받은 뒤 구현한다.
4. 개선·리팩터는 **수정 완료·검증 후** 별도 섹션으로 **제안만** 하거나 다음 작업으로 분리한다.
5. 사용자가 “버그 수정 + 기능 추가”를 한 번에 원하면 **범위를 명시적으로 합의**한 뒤 진행한다.

상세 예시·계획 문구 템플릿은 아래 **Output Format**을 사용한다.

## Step 1: PLANNING (계획 수립)

1. **요구사항 분석**: 구현할 기능의 범위를 명확히 정의합니다. (**Scope & defect handling** 적용.)
2. **규칙 확인 (`code-writing-guard` 사용)**:
   - 기존 구현 중복 여부 검색 (`rg` 활용)
   - 호환성 래퍼 / 레거시 패턴 제외 설계
   - 매직 넘버 대신 상수 사용 계획
3. **계획 문서 작성**: 변경할 파일과 로직을 기술한 계획을 채팅에 출력합니다.

---

## Step 2: EXECUTION (구현)

1. **승인된 계획 범위**에 따라만 코드를 작성합니다. (중간에 떠오른 “추가”는 다시 PLANNING·승인.)
2. 작성 중 규칙 위반 발견 시 즉시 수정합니다.
3. 새 공개 함수·클래스에는 JSDoc 타입 정의를 작성합니다.
4. 새 모듈이면 `module-registration` / `html-registration` 스킬을 따릅니다.
5. **테스트 코드(필수 위치):** 단위·통합·회귀·검증 스크립트 등 **새 테스트 코드는 저장소 루트 `tests/` 이하에만** 작성한다. **신규 배치는** **`tests/<역할요약>_YYMMDD/`** 서브폴더를 새로 만들고 그 안에 둔다 (`code-writing-guard/reference.md` §12). 다른 디렉터리에 테스트 전용 파일을 두지 않는다.

---

## Step 3: VERIFICATION (검증)

1. **통합 검증 실행**: `/verify-implementation`으로 전체 규칙 준수 확인
2. **개별 검증 (필요 시)**: 수정 영역에 따라 선택적으로 실행
   - `verify-grid-algorithm` — 그리드 알고리즘 변경 시
   - `verify-order-execution` — 주문 실행 로직 변경 시
   - `verify-api-routes` — 백엔드 라우트 변경 시
   - `verify-perround-mode` — perRound/marketType 변경 시
3. **자동화 테스트 (선택이지만, 작성 시 위치는 필수)**: 테스트 코드를 추가한다면 **반드시 저장소 루트 `tests/`** 이하에만 둔다. **새 묶음은 `tests/<이름>_YYMMDD/`** 서브폴더에서 진행한다. 실행 방법을 보고에 한 줄 포함 (`code-writing-guard/reference.md` §12).
4. **결과 보고**: 검증 결과를 채팅에 요약합니다. (검증 요약만을 위한 **임의** 리포트 `.md` 를 새로 만들지 않는 것이 기본.)
5. **`docs/` 에 설계·계획 등을 파일로 남길 때 (선택)**: **`/document-authoring`** — 종류별 폴더 + 신규 `*_YYMMDD.md` (`document-authoring/reference.md`).

## Output Format

계획 수립 시 다음 형식으로 채팅에 출력합니다:

```markdown
# [제목] 구현 계획

## 계획 유형 (주 유형 하나 + 부가 시 병기)
- **주 유형**: [버그 수정 | 신규 기능 | 검증·분석] (복수면: 주 유형 + 부가로 명시)
- **이번 턴에 코드 변경 여부**: [예 / 아니오 — 검증·분석만이면 아니오]

## 범위
- **사용자 요청 요약**: [한 줄]
- **이번 작업에 포함**: [요청된 것만 나열]
- **제외(별도 제안만, 승인 전 구현 안 함)**: [있으면 나열 — 임의 추가 금지]

## 불량(버그)인 경우 (주 유형이 버그 수정일 때)
- **최소 수정(현상·원인 위주, 버그 클로즈)**: [파일·행위 — 신규 기능 없이]
- **최소안 불가/불충분 시에만**: [왜 부족한지] → **별도 신규 기능 계획(승인 후)**: [한 줄 요약 또는 “해당 없음”]
- **개선·리팩터 제안 (선택, 수정 검증 후)**: [없으면 “없음”]

## 신규 기능인 경우 (주 유형이 신규 기능일 때)
- **새 동작·설정·범위**: [명시]
- **버그 수정과 섞지 않음**: 같은 PR에 무관한 버그픽스를 넣지 않는다(합의된 범위만).

## 검증·분석인 경우 (주 유형이 검증·분석일 때)
- **분석 대상**: [로그 경로·파일·리뷰 범위]
- **산출**: [결론·이슈 목록]; 코드 변경이 필요하면 **다음 턴 계획**으로 분리

## 계획 (code-writing-guard 확인)
- 중복 검색 결과: [PASS/FAIL]
- 호환성 코드 제외: [확인]
- 상수화 계획: [결과]

## 변경 파일
- [MODIFY] path/to/file.js: 변경 내용 설명
- [ADD] path/to/new_file.js: 생성 이유

## 검증 계획
- 실행할 스킬: /verify-implementation
- 추가 검증: verify-grid-algorithm (그리드 변경 시)
- 테스트 코드: 신규 시 **`tests/<이름>_YYMMDD/`** 서브폴더 + 루트 `tests/` 이하만 (다른 경로 금지) — `code-writing-guard/reference.md` §12
```
